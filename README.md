# polytropos-alpha

Исследовательский Rust-проект для разработки **интеллектуально сильной, компактной рекуррентной LLM**. Сначала ядро должно научиться самостоятельно решать сложные **математические, химические и логические задачи**. Затем во время обучения оно должно научиться решать, какие базовые знания и навыки оставить в параметрах, а какие сохранять во **внешней иерархической латентной памяти на диске**.

**Целевые ограничения (пока не достигнуты):** уровень полезных интеллектуальных возможностей выбранного ориентира Qwen3.8 27B, **3–4 GB весов ядра**, реальное обучение на **одной RTX 5060 с 8 GB VRAM**, высокая скорость и эффективность обучения. Вращающиеся матрицы исследуются как способ сжатия параметров в **10–100 раз** при контролируемой потере качества. Целевые характеристики должны быть подтверждены экспериментами.

**Принцип разделения знаний:** ориентир **20% базовых и связующих знаний в ядре / 80% расширяемых сведений во внешней памяти**. Это не жёсткое соотношение байтов или параметров: ядро учится сохранять способности рассуждать и извлекать нужные знания. Дисковая память может расти независимо от VRAM, должна поддерживать эффективное обучение/обновление и **не загружаться в GPU целиком**. Модель запрашивает только нужные иерархические регионы и выбирает глубину погружения, например «базы данных → PostgreSQL → SQL → SELECT». В VRAM помещаются веса, обязательные вычислительные состояния и лишь ограниченное представление запрошенных данных. **Сетевые и Wiki-адаптеры пока исключены из текущего этапа.**

## Два уровня проекта

**VeriNeural** (`crates/verineural/`) — независимый от архитектуры конструктор вычислений. Пользователь определяет Rust-примитивы, операции и контракты, объединяет их в Semantic Neural IR и получает:

- LLVM NVPTX/PTX и исполнение через **CUDA Graph** на явном non-blocking stream;
- Lean 4-модели и проверку поддерживаемых математических свойств;
- артефакты перевода, проверки ограничений памяти, композиции и доверенных предположений.

VeriNeural **не поставляет готовые LLM, Transformer/Attention, KV cache или обучающий стек конкретной модели**. Они принадлежат потребительским архитектурам в `labs/` и должны собираться из публичного API. Дисковая латентная память и её обучаемая маршрутизация также относятся к конкретной LLM, а не к готовым компонентам библиотеки. Lean-доказательства математической модели не являются доказательствами CUDA JIT/SASS или успешности обучения.

## Среда и основные команды

Инструменты Rust, LLVM NVPTX, CUDA toolkit, Lean 4 и Task определены в `flake.nix`. NVIDIA Driver/GPU требуются на хосте для аппаратных проверок.

```sh
nix develop
task prepare           # cargo fmt и проверка форматирования
task check             # Rust workspace (см. правило auto-format в AGENTS.md)
task test              # CPU/обычные Rust-тесты
task clippy
```

`repospool` доступен в закреплённом Nix devShell. Команда `task prepare` сначала выполняет `repospool generate .`, создавая локальный `.repospool` со снимком **закоммиченного `HEAD`** (незакоммиченные изменения не входят), затем форматирует Rust. Все основные лабораторные команды Taskfile проходят эту подготовку; `task build`, `task clippy` и `task doc` также обновляют снимок без запуска автоформатирования. Если RepoSpool завершится ошибкой, последующая лабораторная команда не запустится. Снимок является генерируемым файлом и игнорируется Git; ручной запуск: `task repospool-generate`.

Специализированные команды из единого [Taskfile.yml](Taskfile.yml):

```sh
task proof-stage3
task verify-certified-build
task lab-xor && task verify-lab-xor
task lab-stage9 && task verify-lab-stage9
task verify-gpu-temporal-bptt
task verify-gpu-batch-transfers
task test-lab-torus16-ema4-checkpoint
```

Задачи `lab-xor` и `lab-stage9` **создают проверяемые файлы в своих лабораториях** (DOT/PNG, Lean, LLVM/PTX, manifests, output bits). Эти файлы считаются **генерируемыми выходами**, в Git не хранятся. Оффлайн `verify-lab-xor` / `verify-lab-stage9` запускают **после** генерации актуального набора. Исходники и обязательства доказательств сохраняются в Rust и Lean.

Для Torus16 сначала изучить [README лаборатории](labs/torus16-mix-0.1.0/README.md) и [план перехода v0.2](labs/torus16-mix-0.1.0/V0.2_TRANSITION.md). **Полный BPTT16 GPU JIT намеренно заблокирован по умолчанию:** большой граф с 63 707 CUDA kernels зависал на загрузке драйверного модуля без нагрузки GPU. `task benchmark-torus16-v02-bptt16` исторически называется benchmark, но сейчас выполняет только безопасный **CPU preflight** без LLVM/CUDA JIT и обучения. Не считать его показателем качества модели.

## Лёгкий CI (без GPU)

GitHub Actions при push в `dev` и `main` генерирует и проверяет `.repospool`,
загружает резервный snapshot в Actions Artifacts на 7 дней, затем запускает
только `cargo test --locked -p verineural --lib --tests`. Тесты с `#[ignore]`
(требующие GPU/Lean/LLVM/Graphviz) не запускаются. **Лабораторные crates
и их задачи через CI не запускаются.** Полная GPU/Lean-приёмка остаётся локальной.

После успешных тестов workflow **коммитит `.repospool` в `dev`** отдельным
fast-forward коммитом от `github-actions[bot]` без force-push; `main` остаётся
только для чтения и тестов. Снимок содержит исходное состояние предыдущего
коммита: сам `.repospool` исключён из индекса RepoSpool, а его запись в Git
создаёт новый SHA, поэтому он не может ссылаться на собственный Git-коммит.
Следующие `task repospool-generate` / `task prepare` учитывают этот случай и
не изменяют содержимое снимка на уже опубликованном artifact-only HEAD.
Публикация выполняется только при успешной генерации, верификации и CPU-тестах;
при конкурентном push обычный fast-forward `git push` отклонит устаревший снимок.

## Правила результатов и верификации

- **Не путать** математические Lean-теоремы, структурный PTX audit, численную CUDA-проверку и неподтверждённую корректность аппаратного исполнения.
- Сообщать размер весов **отдельно** от объёма дисковой латентной памяти; измерять пик VRAM (включая состояния оптимизатора), задержки адресного чтения с диска, время компиляции/JIT, training throughput и время до качества.
- В лабораториях отделять train, validation и test; не выбирать архитектуру по зарезервированному test, сравнивать одинаковый объём обучения и учитывать различия числа optimizer updates.
- Не запускать тяжёлые GPU/Lean/Cargo задачи агентом без явного указания. Пользователь выполняет их на своей RTX 5060 и предоставляет логи.
- Рабочая ветка — только `dev`. `main` не обновляется без прямого поручения. Запрещены самовольные CI/CD и инфраструктурные сервисы.

Текущий репозиторий содержит **исследовательские реализации и проверяемые подмножества**, а не завершённую рекуррентную LLM с 3–4 GB весов и обучаемой дисковой памятью. Историю измерений хранить в профильных документах лабораторий, не раздувать корневой README очередными журналами запуска.
