# VeriGPU: целевая спецификация

**Статус:** архитектурный контракт проекта. **Не является описанием уже реализованных возможностей.**
**Текущий этап:** 1/10, создан импортируемый каркас Rust-библиотеки.

## 0. Назначение, границы и принципы

VeriGPU — **библиотечный Rust-crate** для единого описания, GPU-компиляции и формальной верификации математических вычислений и компонентов нейросетей. Нейросетевая архитектура — будущая **основная программа**, использующая VeriGPU как зависимость, а не часть этой библиотеки. VeriGPU не должен требовать собственного `main` или сервиса.

Единственный пользовательский источник вычисления — Rust-код на поддерживаемом **ограниченном подмножестве** операций VeriGPU; математические требования — явные Rust-контракты и спецификации доверенных примитивов. Из одного типизированного IR должны строиться GPU-программа и Lean 4-модели/доказательства. Произвольный Rust (побочные эффекты, unsafe, произвольный FFI и динамическая рефлексия) **не обещается** переводить или доказывать автоматически. Допустимы ограниченные proc-macro/API-конструкции, если они сохраняют «пишем на Rust» и не требуют ручного LLVM/PTX/Lean.

Приоритет: **KISS, DRY, Pragmatic Engineering, Risk-based Verification, Modular Verification**. Сначала один работающий и честно ограниченный end-to-end сценарий; затем новые примитивы и оптимизации.

## 1. Архитектура

~~~text
                    Rust source + contracts
                             |
                   Rust API / parser / macros
                             |
                       Typed Tensor IR
                             |
                 +-----------+------------+
                 |                        |
           GPU compiler              Proof compiler
       fusion / tiling /             semantics / specs /
       scheduling                   proof obligations
                 |                        |
               GPU IR              Lean 4 model +
                 |                theorems + proofs
              LLVM IR                    |
                 |                 Lean 4 checker
            LLVM NVPTX                   |
                 |                 proof evidence
                PTX                       |
                 |                        |
         CUDA Driver API                  |
           PTX JIT -> GPU                 |
                 +------------+-----------+
                              |
                   numerical validation
                   + certification report
~~~

LLVM NVPTX генерирует **PTX напрямую**; генерация CUDA C++ необязательна. После PTX дальнейшие JIT/ассемблирование в машинный код и исполнение на NVIDIA GPU не становятся автоматически доказанными.

Два backend'а обязаны использовать один семантически определённый Typed Tensor IR. GPU-проходы должны оставлять проверяемый след преобразований.

## 2. Интеграция в Rust и целевой API

- `verigpu` — библиотека `crates/verigpu`, член корневого Cargo workspace.
- В будущем основной crate с нейросетью подключает его через workspace/path dependency. Сейчас основного crate **нет**.
- Целевые API: типизированные тензоры, проверка форм, основные математические операции, компонуемые блоки, Rust-контракты (`requires`, `ensures`, `domain`, `error_bound` либо эквиваленты), компиляция/вызов GPU-ядра и отчёт о сертификации.
- Блоки: Linear / Hidden Layer, MatMul, Bias, Activation, пользовательские чистые математические функции, Routing / Top-K / MoE и композиция сети. **MVP:** forward pass, статические/ограниченные формы, FP32, element-wise операции, простой MatMul, Top-1.
- Формы на уровне Rust предпочтительно проверять статически, если это возможно без сложности; остальные проверять при построении IR/компиляции. Ошибки форм не должны превращаться в ошибку памяти на GPU.
- Компиляция backend'ов не должна требовать вручную писать LLVM IR, PTX или Lean.

Публичный API сначала должен быть узким, без обещаний универсального анализа произвольных Rust-функций. Стабильность API до MVP не гарантируется.

## 3. Typed Tensor IR

Единое типизированное IR хранит:
1. граф чистых операций, зависимости и структуру вызовов/композиции;
2. типы элементов, rank/shape/layout, статические и ограниченные динамические размерности;
3. семантику каждой операции, включая индексацию, broadcast, reduction и обработку ошибок;
4. выбранную FP-политику: rounding, FMA, порядок редукции, denormals/FTZ, NaN/Infinity, signed zero;
5. математический контракт, домен входов, предусловия, постусловия, допустимую ошибку;
6. происхождение операций и идентификаторы, необходимые для трассировки доказательств.

**Инварианты:** корректность типов и форм, однозначная семантика индексов/выходов, явные предположения; неподдерживаемая операция вызывает явную ошибку. Вычислительный IR независим от способа GPU-размещения.

## 4. GPU IR и backend

GPU IR уточняет Tensor IR: распределение по threads/blocks/warps, tiling, реальные буферы и memory space, порядок FP-операций, aliasing, синхронизацию и границы доступа.

Требуются:
- fusion совместимых element-wise операций;
- parallel mapping по элементам/строкам/тайлам;
- tiled MatMul в поддерживаемом подмножестве;
- устранение избыточных промежуточных тензоров;
- lowering GPU IR → LLVM IR → NVPTX → PTX;
- загрузка PTX, allocation/transfer/launch/synchronization через CUDA Driver API.

В сертифицированном режиме каждый проход имеет формализованную корректность: доказанное семантическое правило либо доказанную численную границу. В противном случае проход отключается/сборка не сертифицируется. Отдельно учитывать свойства памяти и синхронизации.

**Граница доверия:** доказательство Tensor IR ↔ GPU IR не доказывает корректность LLVM, NVPTX, PTX JIT, драйвера и самого GPU. Пока соответствующий lowering/исполнение не верифицирован, учитывать его в TCB. GPU-тесты не заменяют доказательства.

## 5. Lean 4 backend и автоматизация доказательств

Из Tensor IR генерировать:
- математическую модель (идеальная арифметика при необходимости) и, отдельно, точную модель конечной FP-арифметики;
- контракты/предусловия и формулировки теорем;
- модель оптимизированной последовательности операций;
- обязательства типов, форм, индексов, границ, корректности примитивов и композиции;
- обязательства сохранения семантики применённых оптимизаций;
- численные оценки там, где поддерживаются.

Доказательства собираются из **уже проверенных лемм**, правил преобразования и автоматических тактик Lean 4. Не придумывать произвольную математическую цель без контракта пользователя/доверенного примитива. Новое пользовательское математическое утверждение может потребовать отдельной доказательной библиотеки.

Сертифицированная сборка **не допускает** `sorry`, `admit`, неконтролируемые пользовательские аксиомы или ложные предпосылки. Контракты с невозможными/пустыми доменами не должны выдавать вводящее в заблуждение «доказательство для всех реальных входов»: указывать предусловия и непустоту/достижимость домена, если это существенно. Успешная проверка Lean подтверждает именно сформулированную теорему в Lean с её зависимостями и доверенной базой.

## 6. FP32 и численные режимы

### 6.1 Strict FP32

- IEEE 754 binary32 для поддерживаемых операций, явно указанное округление (для MVP предпочтительно round-to-nearest ties-to-even).
- Явные правила FMA contraction, порядка редукций, subnormal/flush-to-zero и аппаратных допущений.
- Явная политика для NaN, infinity, signed zero и особых случаев; где payload NaN не гарантирован, не утверждать битовую эквивалентность payload.
- Запрет несертифицированных fast-math, перепорядочивания операций и скрытой пониженной точности.
- Цель: битовая эквивалентность **формальной последовательности FP32-операций** с выбранной операционной моделью GPU при точно указанных условиях. Это не само по себе доказательство корректности аппаратуры.

### 6.2 Bounded Error

Разрешить трансформации порядка/точности только при доказательстве для контракта:

~~~text
forall x in Domain:
    norm(GPU_model(x) - MathSpec(x)) <= epsilon
~~~

`GPU_model` — формальная модель фактической последовательности вычислений, а не измерение на GPU; `MathSpec` — эталонная математическая функция. Контракт явно задаёт domain, norm, epsilon и предположения о диапазонах/отсутствии неопределённых случаев. Для недоказанного bound статус — **не сертифицировано**, независимо от численных экспериментов.

## 7. Модульная и композиционная верификация

Каждый примитив/блок имеет локальный контракт и доказательство: корректность формы, индексов, операции и её численной семантики.

- Linear / Hidden Layer: матричное произведение, смещение, активация, совместимость размерностей.
- MoE Router / Top-1: корректный выбор индекса, явная политика ties, NaN/Infinity, допустимости индексов и нормализации, если она применяется.
- Top-K/MoE после MVP: правила сортировки/связности, корректность весов, маршрутизация и boundary cases.
- Expert: соответствие своей спецификации.
- Network (в будущем в основном приложении): композицией доказать свойства композиции **при выполнении предусловий блоков**.

Проверка forward pass не означает доказательства сходимости обучения, качества прогнозов или корректности gradient/backprop.

## 8. Сертификация: уровни, доверенная база, проверка на GPU

| Уровень | Что может быть доказано | Ограничение |
|---|---|---|
| Mathematical | модель операции/функции удовлетворяет заданному математическому контракту | Только в указанном домене, для явной модели и её предпосылок |
| Transformation | применённые IR-оптимизации сохраняют заявленную семантику/ограничение | Не распространяется автоматически на невeрифицированный lowering |
| Numerical | formal GPU FP32 model соответствует строгой FP32-модели либо доказанной границе ошибки | Требует конкретного FP-профиля, формы и входного домена |

Численный запуск GPU и сравнение с независимым эталоном — **validation** (эмпирическая проверка), а не четвёртый формальный уровень. Допускаются отдельные сертификаты конкретных результатов лишь при наличии строго описанного метода.

TCB явно перечисляет модель примитивов, Lean kernel, LLVM/NVPTX, PTX JIT, драйвер/оборудование и любые непроверенные bindings/предпосылки, пока они действительно доверенные. Отсутствие доказательства машинного исполнения нельзя маскировать названием файла `certificate.json`.

Каждый уровень может иметь статус `proven`, `failed`, `not_applicable`, `unsupported`; `validated` зарезервирован для эмпирического результата и не равен `proven`. Для `proven` необходимы проверенные доказательные артефакты и указание области действия.

## 9. Артефакты и формат отчёта

Целевая структура (генерируется позднее; **на этапе 1 отсутствует**):

~~~text
target/verigpu/
├── network.ll
├── network.ptx
├── model.lean
├── specs.lean
├── proofs.lean
├── certificate.json
└── validation.json
~~~

`certificate.json` содержит:
- уровень и статус каждого вида сертификации, ссылки на проверенные теоремы, явно объявленные предпосылки;
- хеши исходного Rust-кода, Tensor/GPU IR и артефактов;
- версии VeriGPU, rustc, Lean, LLVM, CUDA toolkit/driver и целевую GPU-архитектуру;
- strict/bounded FP32 profile, формы и домен, разрешённые оптимизации;
- состав TCB и границу между формально проверенным, доверенным и эмпирическим.

`validation.json` хранит среду запуска, входные случаи/seed, эталон, наблюдаемое расхождение и результаты; ни одна статистика тестов не меняет автоматически formal status.

Артефакты генерируются детерминированно настолько, насколько позволяет инструментальная цепочка; хеши должны соответствовать реально проверяемым файлам.

## 10. Целевой интерфейс сборки

~~~sh
cargo verigpu build --profile certified
~~~

Это **планируемый** UX, сейчас команда не существует. `cargo verigpu` допускается как отдельный cargo subcommand в будущем, но не как обязательное автономное приложение/вторая основная программа. Для локальных операций весь пользовательский процесс должен быть доступен через **Taskfile** (например, `task certify` после реализации; не добавлять пустую заглушку сейчас).

Сертифицированная сборка выполняет:
1. разбор поддерживаемого Rust/API и статическую проверку;
2. построение Typed Tensor IR и валидацию контрактов;
3. семантически допустимую оптимизацию и GPU lowering;
4. эмиссию LLVM IR/PTX;
5. эмиссию Lean-моделей, спецификаций и proof terms/tactics;
6. запуск Lean checker, fail-closed при недоказанных обязательствах;
7. при доступном GPU — отдельную численную валидацию и отчёт.

Если обязательная цель недоказана, **certified build завершается ошибкой** с указанием условия/уровня. Недоступность GPU не должна выдавать validation pass; режимы без GPU и строгость требуемой validation задаются явно.

## 11. MVP и критерий готовности

Первая поддержка: прямой forward pass, FP32, ограниченные формы, element-wise fusion, простой MatMul и Top-1 routing. После MVP: сложный Top-K/MoE, Tensor Cores, mixed precision, backprop и обучение. Универсальной автодоказуемости произвольной математики нет.

**Критерий MVP:** одна пользовательская Rust-функция через VeriGPU строит корректный Tensor IR, создаёт исполняемый GPU kernel, имеет Lean 4 доказательства заявленных свойств; отчёт без двусмысленности разделяет `proven`, `validated` и `trusted/unsupported`, включая backend/driver trust boundary.

**Критерий этапа 1:** workspace, импортируемая библиотека-заготовка, root `flake.nix`, Taskfile, правила агентов, данная спецификация и дорожная карта. На этапе 1 доказательства и GPU-исполнение отсутствуют.
