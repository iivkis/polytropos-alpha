# VeriGPU: 10 крупных этапов реализации

**Порядок:** сначала библиотека VeriGPU, затем (по отдельному решению) основная нейросетевая архитектура. Каждый этап — крупный вертикальный результат, а не многодневное дробление очевидных действий. Дорожная карта описывает **будущую работу** и не объявляет её выполненной.

**Принципы:** KISS · DRY · Pragmatic Engineering · Risk-based Verification · Modular Verification. Доказать ограниченное корректно лучше, чем поддерживать всё номинально.

## 1. Инициализация workspace и контрактов проекта — ТЕКУЩИЙ ЭТАП

**Объём:** Cargo workspace в корне, импортируемый crate `verigpu` без `main.rs`, корневой Nix flake с Rust/LLVM/CUDA/Lean/Task, Taskfile для локальных команд, `agents.md`/указатель `AGENTS.md`, SPEC и ROADMAP. Никаких GPU-функций, формальных доказательств, CI и нейросети.

**Готово, когда:** файлы лежат в репозитории, crate можно указать как Rust dependency; явно сказано, что функциональность и тестирование пока отсутствуют. Сборки не запускать от имени агента без запроса.

## 2. Рабочий Rust API + Typed Tensor IR

**Объём:** маленький, но полноценный публичный набор Tensor/Shape/Graph, модель чистой функции/контракта, формы и операции add/mul/element-wise map; ошибки несогласованных форм; один фронтенд из Rust в типизированный граф. Запрет на «доказательство произвольного Rust»: подмножество явно определено.

**Готово, когда:** реальная Rust-функция собирает и валидирует IR; можно сериализовать/инспектировать граф и показать отказ при неверной форме. Это основа для обоих backend'ов, без дублирования семантики.

## 3. Математическая семантика IR и первая Lean-модель

**Объём:** формализация базовых тензоров, индексов и element-wise операций, контрактов входов/выходов; генератор Lean 4 `model/specs/proofs` на ограниченном фрагменте; библиотека проверенных лемм; чистые обязательства, без `sorry`.

**Готово, когда:** одна Rust-функция порождает Lean-файлы, Lean проверяет нетривиальную корректность формы/операции; недоказанные обязательства явно блокируются. GPU ещё не обещан.

## 4. Минимальный end-to-end GPU backend

**Объём:** GPU IR, threads/blocks mapping для element-wise, LLVM IR → NVPTX → PTX, минимальный Rust CUDA Driver API runtime, управление буферами и kernel launch, явная стратегия хостового драйвера.

**Готово, когда:** та же Rust-функция исполняется на NVIDIA GPU и совпадает с эталоном на локальных тестовых данных в определённом профиле. Результат GPU — пока **validated**, не «доказан аппаратно».

## 5. Первый замкнутый проверяемый вертикальный срез

**Объём:** связать Rust-контракт, семантику IR, доказательство Lean и запуск GPU; определить минимальные правила lowering, критичные инварианты индексов/памяти и TCB; первый `certificate.json` + `validation.json` с честными статусами.

**Готово, когда:** один вызов демонстрирует весь путь Rust → IR → Lean/LLVM/PTX → GPU → отчёт; все заявленные теоремы проверяются Lean, backend trust boundary указан явно. Fail-closed при неудаче proof.

## 6. Сертифицированные оптимизации element-wise

**Объём:** fusion и удаление промежуточных тензоров; проверяемые правила допустимых преобразований; контроль FP-порядка в strict-режиме; трассировка применённых passes.

**Готово, когда:** fused GPU kernel выполняется, оптимизация либо имеет доказательство эквивалентности, либо не допускается в certified mode; есть сравнение с нефьюженной семантикой.

## 7. MatMul, Bias, Activation и tiling

**Объём:** операции линейного/скрытого слоя как **примитивы VeriGPU**, а не готовая нейросеть; формы, layouts, memory access, tile scheduling, композиционные Lean-контракты; минимальное сравнение производительности/точности.

**Готово, когда:** линейный блок компилируется в полезный GPU-код, границы тайлов безопасны, формы/контракты доказаны, оптимизации учитывают FP-режим.

## 8. Strict FP32 + Bounded Error как проверяемые профили

**Объём:** явная IEEE-754 binary32 semantics для поддерживаемых инструкций/случаев; rounding/FMA/FTZ/NaN/Inf/signed zero, запреты fast-math; отдельно сертификаты ошибок для выбранных редукций/трансформаций с доменом и ε.

**Готово, когда:** strict обеспечивает доказуемые свойства формальной FP-модели (битовая эквивалентность, где она обоснована), bounded режим обеспечивает формальный bound только для поддерживаемых операций; неизвестные случаи возвращают `unsupported`, а не успех.

## 9. Routing / Top-1 и модульная композиция

**Объём:** Top-1 routing, политика ties/NaN, допустимые индексы, композиция примитивов в блоки, доказательства предусловий и постусловий. Top-K/MoE в полной общности пока не делать.

**Готово, когда:** набор проверенных блоков можно композиционно собрать из обычного Rust и получить Lean-доказательства выбранных инвариантов, GPU-исполнение и разграниченный отчёт. **Основную архитектуру не создавать.**

## 10. Интеграция сборки, сертификаты, полировка MVP

**Объём:** окончательный публичный API; `cargo verigpu build --profile certified` и соответствующая команда Taskfile, deterministic outputs/хеши, version/profile/TCB metadata, diagnostics/fail-closed, документация минимального приложения-потребителя.

**Готово, когда:** внешний Rust crate может подключить VeriGPU как dependency и получить рабочий forward-pass GPU kernel + проверенные Lean-утверждения; статусы Mathematical / Transformation / Numerical, validation и доверенные допущения не смешиваются. После этого **отдельно** начинать основную нейросетевую архитектуру.

## Ограничения управления работой

- Не добавлять CI/CD, workflows, git hooks, контейнеры или иную инфраструктуру без явного согласия пользователя.
- Команды сборки/тестирования определяются в Taskfile и обычно запускаются **самим пользователем локально**, а не агентом.
- Не переходить к следующему этапу ради одной косметической перестановки; каждый этап заканчивать реальным, демонстрируемым результатом и честно ограниченной областью поддержки.
- Пересмотр этапов допустим по инженерным причинам, но изменения фиксировать в документе, не превращая 10 этапов в бесконечную серию микро-шагов.
