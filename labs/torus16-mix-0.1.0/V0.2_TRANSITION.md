# Torus16-Mix 0.2.0: переход и критерии приёмки

**Актуальное решение P0 (31 октября 2026):** для локальной RTX 5060
BPTT16/32 исключены из плана качества и обучения Torus16. Рабочая база
P0 — Role-Delta rank4/BPTT4; BPTT8 только отдельным явным экспериментом.
Исторические разделы ниже документируют старую диагностику BPTT16,
а не предлагают её запускать. Текущий P0 entrypoint:
`task train-torus16-p0`. Статус: код подготовлен, аппаратная
приёмка и снижение NLL ещё не измерены.

**Статус:** экспериментальный переход от сохранённого базового
`torus16-mix-0.1.0`; **не** выпуск новой версии и **не** повышение
версии библиотеки VeriNeural. Пока нет проверенного нового архитектурного
варианта, рабочий код и checkpoint 0.1.0 остаются нетронутым baseline.
Отдельный пакет `labs/torus16-mix-0.2.0/` создаётся тогда, когда
появится первая реально отличающаяся и протестированная архитектура.

## Мотивация и реализованная база

Первая версия исследовала TorusShared, Independent и низкоранговые
Role-Delta rank 2/4/8. Из прошлых экспериментов следует, что лучшее
сообщённое Test BPC было 2.444471 у Independent на BPTT=4, seed=0;
тестовый отрезок лишь 512 символов и неоднократно использовался при
принятии решений. Его нельзя считать честной финальной проверкой 0.2.0.

В рабочем v0.1.0 уже реализованы:

- Role-Delta rank 4/8 и отдельный weight-only warm-start от TorusShared;
  перенос AdamW moments и training cursor между архитектурами запрещён.
- Универсальный temporal BPTT=4/8 на публичном VeriNeural Semantic IR;
  parameter-only hoisting сокращает IR/kernels без изменения архитектуры.
- Packed D2H + packed H2D через CUDA Graph на non-blocking stream;
  полный CPU AdamW checkpoint совпал побитово в проверенном сравнении
  с отдельными transfer-путями.

Последний парный benchmark (26 октября 2026, BPTT=4, rank=4,
256 окон, 64 validation chars, CPU AdamW, packed D2H/H2D):

| Режим | Прогон 1, токенов/с | Прогон 2, токенов/с | Replay, мс (1/2) |
|---|---:|---:|---:|
| Baseline IR | 259.15 | 254.63 | 13.3087 / 13.3365 |
| Parameter hoisting | 271.09 | 271.12 | 12.7602 / 12.7782 |

Среднее ускорение обучения hoisting относительно baseline IR
составляет ~5.5% при двух повторениях. Validation BPC в четырёх
прогонах равнялась 1.970608 **только на 64 символах**. Checkpoint
совпали побитово между повторами внутри каждого IR-режима; **между
разными IR-режимами** побитовое равенство не требуется из-за отличий
порядка FP32-редукций и идентификатора тренировочного графа.

Численные тесты GPU и совпадение checkpoint не означают формального
доказательства Lean об аппаратном FP32/LLVM/PTX/SASS.

## Этап 0.2-A: горизонт градиента и Role-Delta

**Готовый entrypoint:**

```sh
task verify-gpu-temporal-bptt
task verify-gpu-batch-transfers
task benchmark-torus16-v02-horizon
```

Это одна матрица экспериментов: Role-Delta rank 4/8 × BPTT 4/8,
weight-only warm-start от **одного и того же** TorusShared checkpoint.
На всех четырёх вариантах:

- ровно `TORUS16_V02_TRAIN_TOKENS` новых обучающих символов (по
  умолчанию 4096, допустимые значения 8–32768 кратно восьми);
- BPTT4 использует вдвое больше optimizer updates, чем BPTT8.
  Равенство символов **не изолирует чистый эффект горизонта**; для
  причинного вывода потребуются отдельные контроли по числу updates/LR;
- режимы `PACKED_D2H=1`, `PACKED_H2D=1`,
  `HOIST_PARAMETER_ONLY=1` и CPU AdamW; здесь оптимизации runtime
  одинаковые, различаются только rank и горизонт;
- первый 8192-символьный отрезок исторического holdout служит длинной
  validation (reset-state streaming); последний 8192-символьный
  отрезок резервируется, но **не читается** во время обучения;
  `TORUS16_SKIP_TEST=1`. Эти отрезки одного корпуса не заменяют
  новый независимый test;
- одна evaluation в конце при одинаковом числе обученных символов,
  независимые каталоги checkpoint для каждого training IR;
- замеряют подготовку GPU, число kernels, replay, throughput,
  validation BPC и отсутствие чтения test.

Не сравнивать побитово checkpoint разных rank/BPTT. Продолжать от
checkpoint другого тренировочного графа нельзя: для нового BPTT нужно
новое обучение с weight-only warm-start, а не подмена resume.
Актуальный entrypoint ограничивает BPTT значением 8; сначала принять
его GPU память/градиенты/качество, затем масштабировать до 16.

**Критерий завершения 0.2-A:** четыре успешных локальных запуска,
GPU temporal test на восьми шагах, отсутствие чтения test,
отсутствие ошибок CUDA memory/Graph; таблица стоимости GPU и
validation BPC с явным числом training characters и optimizer updates.
Критерии для первого GPU-прогона выполнены, подробные результаты
и обнаруженный блокер масштабирования приведены ниже. Это не
релиз готовой архитектуры 0.2.0.

## Результаты 0.2-A: первый GPU-прогон (26 октября 2026)

**GPU acceptance пройден:** обе игнорируемые GPU temporal проверки,
включая forward/VJP на восьми шагах; packed-transfer parity также
прошёл. Все четыре долгие validation завершились, reserved test не
просматривался. Изменения в коде после этого прогона ещё должны быть
проверены локально.

| Role-Delta | BPTT | Optimizer updates | IR nodes | CUDA kernels | GPU setup, с | Replay, мс/окно | Train, токенов/с | Validation BPC (8192 chars) |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| rank 4 | 4 | 1024 | 7279 | 15865 | 6.925 | 13.2467 | 260.13 | 3.327168 |
| rank 4 | 8 | 512 | 14067 | 31759 | 391.979 | 26.8012 | 273.31 | **3.139470** |
| rank 8 | 4 | 1024 | 7279 | 15865 | 117.545 | 13.2001 | 255.30 | 3.349920 |
| rank 8 | 8 | 512 | 14067 | 31759 | 355.892 | 25.8478 | 280.38 | 3.153746 |

**Ограничения сравнения:** один seed, 4096 обучающих символов,
различное число обновлений AdamW при BPTT=4/8, один исторический
корпус, одинаковый ранее используемый warm-start, один длинный
validation. Побитовое сравнение checkpoint между rank/BPTT не
имеет смысла. Результат не доказывает, что BPTT=8 всегда лучше;
rank 8 по качеству пока проигрывает rank 4 на обоих горизонтах.
Test остаётся закрытым.

**Блокер 0.2-B:** подготовка CUDA на BPTT=8 может занимать почти
6.5 минуты вместо 6.9 секунд для rank4/BPTT4. У rank8/BPTT4 тоже
наблюдается 117.5 секунд при том же числе kernels. По одному
суммарному таймеру нельзя отличить LLVM NVPTX, PTX JIT,
`cuModuleGetFunction`, выделение device buffers, graph capture
и `cuGraphInstantiate`. Это не свидетельство доказанной
асимптотической деградации самого графа.

### Диагностика подготовки

VeriNeural включает **opt-in профилирование** через
`VERINEURAL_GPU_PREPARE_PROFILE=1`. Оно печатает две серии строк:

- `gpu_nvptx_stage=llc / translation_audit`;
- `gpu_prepare_phase=preflight / lower_and_audit /
  cuda_module_load / allocate_and_initial_h2d /
  memory_contracts / kernel_resolution / graph_capture /
  graph_instantiate / total_before_execution`.

Проверять прежде всего `cuda_module_load` (включает CUDA JIT),
`kernel_resolution` и `graph_instantiate`. Это время на host,
а не CUDA device event. Не считать наличие логов ускорением.

Для изолированного воспроизведения rank4/BPTT8 с 64 обучающими
символами и **отдельным каталогом**, чтобы не затереть готовые
4096-char checkpoint:

```sh
VERINEURAL_GPU_PREPARE_PROFILE=1 \
TORUS16_V02_RANKS=4 TORUS16_V02_BPTTS=8 \
TORUS16_V02_TRAIN_TOKENS=64 \
TORUS16_V02_DIR=target/torus16-v02-setup-probe \
task benchmark-torus16-v02-horizon
```

Аналогично `TORUS16_V02_RANKS=8 TORUS16_V02_BPTTS=4`
поможет исследовать аномалию rank8/BPTT4. Базовый task
по-прежнему запускает все четыре конфигурации с validation
8192 chars, если фильтры не заданы. Минимизировать полный
CUDA setup/подготовку PTX можно только после атрибуции
затрат. До этого BPTT=16 не переносить в default.

### Пофазная диагностика rank4/BPTT8 (26 октября 2026)

Разовый повтор с `VERINEURAL_GPU_PREPARE_PROFILE=1` завершился:
14.202 с общего compile+CUDA setup, хотя первый 4096-символьный
rank4/BPTT8 запуск сообщал 391.979 с. Граф **не стал меньше**:
14 067 IR-узлов и 31 759 CUDA kernels в обоих прогонах.
Без профиля первоначального запуска нельзя определить, был ли это
холодный CUDA JIT, давление на ресурсы либо другой временный фактор.

| Этап подготовки training graph | Время, мс |
|---|---:|
| LLVM NVPTX llc -O0 | 8726.274 |
| Структурный LLVM/PTX translation audit | 1154.771 |
| CUDA module load (с возможным JIT) | 1440.381 |
| Разрешение CUDA-функций | 1918.116 |
| Выделение и исходные H2D | 172.481 |
| CUDA Graph capture | 111.647 |
| CUDA Graph instantiate | 292.604 |
| Вся `GpuEngine::prepare` без подготовки holdout | 13875.366 |

Эти стадии измерены через host wall clock.
`graph_capture` и `graph_instantiate` вместе занимают лишь
около 0.40 с, поэтому ускорять именно CUDA Graph constructor
без дополнительных данных нецелесообразно. В повторном прогоне
главный фиксированный расход времени приходится на LLVM `llc`.
Но CUDA JIT/кеш не исключён как причина ранее наблюдавшегося
многоминутного выброса.

**Новый воспроизводимый setup-gate:**

```sh
task benchmark-torus16-v02-setup-stability
```

Это три независимых запуска rank4/BPTT8 по 64 обучающих символа,
с сохранением трёх раздельных журналов фаз и checkpoint,
побитовым `cmp` каждого final/best checkpoint против trial1.
Внутри используется короткая 64-символьная validation и
`TORUS16_SKIP_TEST=1`. Режим **только для performance diagnostics**:
сравнивать по BPC с полным 8192-символьным gate нельзя.
Команда не очищает и не отключает CUDA caches, поэтому различия
между процессами лишь выявляют вариацию, но не доказывают
влияние кеша. Для полного исследования cold-cache нужны
отдельные контролируемые системные эксперименты.

При ручном запуске `benchmark-torus16-v02-horizon` разрешён
`TORUS16_V02_VALIDATION_CHARS=64` только для аналогичной
диагностики; default остаётся **8192**. Не использовать короткую
validation для выбора rank/BPTT или нового архитектурного checkpoint.

## Этап 0.2-B0: контролируемая консолидация GPU allocations

**Экспериментальный код (GPU unit parity пройден):** универсальный
`GpuEngine::with_allocation_slab(true)` теперь размещает материальные
входы и выходы Semantic IR внутри **одного** device allocation.
Адреса всех входных/выходных тензоров остаются уникальными;
zero-copy aliases сохраняют адрес оригинала. CUDA Graph, LLVM/PTX,
порядок вычислений, контракты операций и checkpoint identity не
меняются. Основное отличие: вместо множества `cuMemAlloc_v2`
используется одно выделение на граф; выделение под служебные
GPU feedback/readback buffers может оставаться отдельным.

Критическая граница безопасности: `CudaSession::allocate_batch`
регистрирует **логические размеры каждого подбуфера** для
`require_allocation`. Проверка не должна позволять исходному
kernel писать в соседнюю область только потому, что обе
области размещены в одном CUDA allocation. Общий base
освобождается при завершении CUDA session ровно один раз.

Это **opt-in**, в лаборатории `TORUS16_GPU_ALLOCATION_SLAB=1`.
Старый путь по умолчанию не меняется. Большой contiguous allocation
может не уместиться при фрагментации VRAM даже когда отдельные
allocation успешны: отказ должен оставаться явным, без
недокументированного fallback. Обе модели могут использовать
одинаковый Semantic IR при разных физических адресах.

Проверки:

```sh
task verify-gpu-batch-transfers
task benchmark-torus16-v02-allocation-slab
```

Первый тест содержит отдельный GPU parity case для slab и
отдельных тензоров на трёх эпохах, включая повторный packed
H2D/D2H. Второй выполняет rank4/BPTT8 на 64 обучающих и
64 validation символах, **не читает test**, измеряет
`gpu_prepare_allocations` и стадии CUDA setup и требует
побитового совпадения двух final и best checkpoint.
Длинная 8192-символьная validation не относится к
performance smoke. Никаких claims ускорения до успешной
локальной NVIDIA-проверки.

**Первый локальный прогон (26 октября 2026):**
`task verify-gpu-batch-transfers` завершился успешно: 2 из 2
NVIDIA GPU-тестов прошли, включая slab against separate parity.
`task benchmark-torus16-v02-allocation-slab` был остановлен на
первом `grep` диагностических строк, а не на reported CUDA
error: вложенный task печатал только отфильтрованные данные,
тогда как `gpu_allocation_mode` и `gpu_prepare_allocations`
остались в `$base/separate/rank4-bptt8.log`.
Внешний benchmark исправлен и читает **сырой training log**
каждого режима, отдельно сверяя фактически включённый
`gpu_allocation_mode`. Побитовое сравнение checkpoint
между режимами и показатели ускорения этим первым прогоном
**не установлены**.

**Решение о BPTT=16:** не включать его в default до
сравнения потребления VRAM и реального эффекта slab.
Даже если ускорятся allocations, останется стоимость
`llc` и разрешения десятков тысяч kernel-функций.
Масштабирование требует явного подтверждения и поэтапной
проверки VJP. Slab не даёт Lean-доказательства корректности
CUDA/LLVM/PTX/SASS.

### 0.2-B0: NVIDIA acceptance slab и решение по распределению памяти

Локальный NVIDIA запуск завершился: `verify-gpu-batch-transfers`
прошёл **2/2** (включая parity отдельной vs slab памяти).
Затем `benchmark-torus16-v02-allocation-slab` прошёл `cmp`
final и best checkpoint.

| Режим | CUDA allocations | Allocate+initial H2D | Full compile+prepare |
|---|---:|---:|---:|
| Separate | 32 229 | 135.146 мс | 13.930 с |
| Slab | 1 | 32.183 мс | 13.482 с |

Это примерно −76.2% локальной стоимости начального выделения и
−3.2% **общего** setup. Восьмиоконный train throughput вырос
с 225.62 до 232.00 токенов/с, но выборка слишком короткая
для выводов о реальном приросте обучения. Никакого влияния
на качества модели из этого прогона не следует.

**Решение:** оставить slab опциональным. Условная экономия
на `cuMemAlloc` не устраняет `llc` и тысячи kernel symbols.

### 0.2-B1: BPTT=16, bounded GPU smoke

Публичное `unroll_model` уже разрешает **до 16 шагов**.
Лабораторный `ema4_bptt` теперь допускает `TORUS16_BPTT=16`,
сохраняя default 2 и прежний BPTT4/8 без изменения поведения.
Новая 16-шаговая траектория является **экспериментом**, а не
сертифицированной или рекомендуемой конфигурацией.

До `llc`, CUDA JIT и device allocations измеряются:
`program.kernel_count()` и `GpuProgram::tensor_allocation_bytes()`.
Исторически в режиме BPTT16 использовалось ограничение
**70 000 CUDA kernels и 512 MiB** основных тензорных
буферов (пределы регулируются `TORUS16_BPTT16_MAX_KERNELS`,
`TORUS16_BPTT16_MAX_TENSOR_MIB`). Если превышен хотя бы один,
выдаётся ошибка без попытки NVIDIA JIT. Эти байты **не включают**
CUDA Graph metadata, PTX/JIT, staging, служебные графы и драйверную
память; это не измерение пикового VRAM. При ошибке реального
выделения также должен быть fail-closed, без незаметного fallback.

GPU acceptance-тест `temporal_parameter_hoisting_gpu_forward_and_gradients_match_baseline`
расширен с горизонтов 3/8 до 3/8/16. В BPTT16 он применяет
physical slab к обеим сравниваемым IR-траекториям;
forward требуется совпадение побитово, parameter VJP
сравнивается численно с явной погрешностью. Дополнительно
CPU структурный тест проверяет терминальное состояние,
16 cotangent nodes и формы производных.

Команды проверки и безопасной диагностики приведены в
подразделе **BPTT16 PTX JIT incident** ниже. Историческая
короткая попытка BPTT8/16 на 64 train/validation символах
дошла до блокирующей загрузки монолитного PTX BPTT16.
Результатов тренировки BPTT16, validation BPC или peak VRAM
эта попытка **не дала**. Результаты BPTT8 отдельно получены,
но их нельзя использовать для выбора BPTT16.

**Граница гарантий:** маленькие GPU BPTT16 temporal/VJP
тесты пройдены, однако полная Torus16-Mix BPTT16 всё ещё
не является принятой GPU конфигурацией. LLVM/PTX/SASS и
аппаратная FP32-корректность формально не доказаны.

### 0.2-B1: BPTT16 PTX JIT incident и обязательный fail-fast (26 октября 2026)

**Локальный запуск GPU parity прошёл:** 2/2
`task verify-gpu-temporal-bptt`, включая игрушечный BPTT16
с малым числом CUDA-функций. Но **это не проверка большой
архитектуры Torus16-Mix с BPTT16**.

Большой эксперимент `benchmark-torus16-v02-bptt16`
после успешного BPTT8 дошёл до BPTT16 и был прерван пользователем.
Исходные диагностические строки:

- `temporal_ir_nodes=27643`,
  `cuda_graph_after=63707` и `tensor_bytes=26971644`;
- `llc`: 17.852 с, `translation_audit`: 2.659 с;
- `gpu_prepare_phase=lower_and_audit elapsed_ms=20601.983`;
- **нет** последующей строки `cuda_module_load` до Ctrl+C,
  и GPU оставался без вычислительной нагрузки.

Последний активный вызов находится в
`CudaSession::new(&ptx)`, где драйвер загружает модуль
(`cuModuleLoadData`) с десятками тысяч отдельных PTX kernels.
Фазовый журнал не доказывает точную внутреннюю операцию драйвера,
но указывает на блокировку **до CUDA Graph capture/replay**.
Лимит 70 000 был опасно завышен и не учитывал CPU/JIT стоимость.
Размер tensor slab ~25.7 MiB ничего не говорит о стоимости
генерации/компиляции CUDA-функций.

**Исправление безопасности:**

- `TORUS16_BPTT16_MAX_KERNELS` по умолчанию уменьшен до
  **40 000**, но это лишь консервативный бюджет числа функций,
  а не гарантия определённого времени JIT.
- Даже если граф укладывается в бюджеты, полноценный
  BPTT16 CUDA JIT **запрещён по умолчанию** и требует
  `TORUS16_BPTT16_ENABLE_SLOW_JIT=1`.
- `TORUS16_BPTT16_PREFLIGHT_ONLY=1` завершает
  `ema4_bptt` **после создания и оценки CPU IR**, но до
  `GpuEngine::lower`, CUDA module load и создания CUDA Graph.
  Печатает `over_budget` и
  `bptt16_preflight_only=PASS cuda_jit=SKIPPED ...`.
  Не обучает, не валидирует, не открывает test, не создаёт checkpoint.
- Сохранённое имя `task benchmark-torus16-v02-bptt16`
  теперь намеренно запускает **только безопасный CPU preflight**,
  без BPTT8, без GPU и без скрытого CUDA JIT. Это больше
  **не benchmark** несмотря на историческое имя команды.

```sh
git pull --ff-only
task benchmark-torus16-v02-bptt16
```

Перед продолжением реального BPTT16 нужен архитектурно-нейтральный
способ уменьшить число **уникальных PTX kernel entrypoints**,
например проверяемая переиспользуемая kernel specialization/
deduplication, сохранив адреса, параметры, зависимость узлов
IR и GPU/Lean границы гарантий. Измерять следует отдельно
`llc`, `cuModuleLoadData`, `cuModuleGetFunction` и
`cuGraphInstantiate` на bounded примерах. Запуск монолитного
модуля на 63 707 kernels без явного разрешения больше
не является приёмочным этапом.

## Следующие экспериментальные этапы

1. **P0: доступное обучение.** Оставить BPTT4 основным; BPTT8
   как явную, ограниченную по ресурсам альтернативу. Обучение вести
   двумя этапами LR=0.002 → 0.0004 с сохранением AdamW moments,
   длинной validation, закрытым test, учётом NLL в натах и BPC.
   Отказ от BPTT16/32 окончателен для данного плана качества; их
   исторический экспериментальный код не удаляется из VeriNeural.
2. **0.2-C: динамическая EMA.** Зависимый от входа decay
   `alpha_t = sigmoid(b + f(x_t))` с обязательным ablation против
   *того же* лучшего Role-Delta/BPTT без динамического decay.
   Композиция только из универсальных примитивов VeriNeural.
3. **0.2-D: устойчивое увеличение глубины.** 6/8 блоков и
   управляемый residual scale после успешных BPTT/decay ablations.
4. **0.2-E: подтверждающее качество.** Отдельный evaluator
   на ранее не использованном корпусе с validation/test не менее
   8192 символов, фиксированный tokenizer/alphabet mapping, явный
   reset/warm-up протокол, несколько *полных* seeds. Ранее
   просмотренный 512-символьный test использовать только как
   историческую статистику, не выбирать по нему гиперпараметры.

Целевые значения (например, Test BPC ≤ 1.5) являются гипотезами,
а не обещаниями. Решение о версии 0.2.0 требует воспроизводимого
улучшения времени до одинаковой длинной validation BPC без
неприемлемого роста CUDA kernels/VRAM и с явным отчётом об
уровне формальной верификации. Динамическую EMA и рост глубины
нельзя смешивать в одном первом эксперименте, иначе невозможно
приписать изменение качества конкретной причине.

## 0.2-B: BPTT=16 GPU-JIT и graph replay diagnostic gate (ожидает аппаратной приёмки)

После интернирования идентичных NVPTX-функций размер модуля и число
CUDA Graph launches больше не совпадают. Раннер `ema4_bptt` публикует
`gpu_compilation_inventory`: `graph_kernels`, `unique_functions`,
`llvm_ir_bytes`, `graph_tensor_bytes`. Последнее значение учитывает
только материализованные тензоры графа, **не** peak VRAM, драйвер,
CUDA Graph, PTX JIT или staging-буферы.

BPTT=16 сохраняет fail-closed ограничение `TORUS16_BPTT16_MAX_KERNELS`
(40 000 graph nodes по умолчанию) и добавляет самостоятельный предел
`TORUS16_BPTT16_MAX_UNIQUE_KERNELS` (4096). Вместе с
`TORUS16_BPTT16_MAX_TENSOR_MIB` (512) они проверяются **до LLVM и CUDA**.
Превышение хотя бы одного лимита запрещает GPU-подготовку.
`TORUS16_BPTT16_PREFLIGHT_ONLY=1` остаётся CPU-only. Для реального
BPTT=16 требуются одновременно явное согласие
`TORUS16_BPTT16_ENABLE_SLOW_JIT=1` и допустимые бюджеты.

`TORUS16_SETUP_PROBE_ONLY=1` собирает фактический supervised forward/VJP
training IR и делает один синхронизированный CUDA Graph replay,
проверяет конечность выбранных logits и затем измеряет CUDA-event
replay (один warmup, три повтора). Он завершает работу **до AdamW,
checkpoint write/delete, validation и test**. Этот режим не оценивает
sample efficiency, BPC или устойчивость обучения и не изменяет
математическую семантику.

`task profile-torus16-bptt16-interning` сначала проверяет unit gate и
запускает CPU-only BPTT=16 preflight. С установленным
`TORUS16_PROFILE_RUN_GPU=1` запускает BPTT=8 и 16 GPU probes с
раздельными логами и конечным таймаутом. Только в этом **явно
разрешённом диагностическом запуске** предел graph nodes повышается
до 80 000; предел PTX entrypoints (4096) и графовых тензоров (512 MiB)
не снимается. `VERINEURAL_GPU_PREPARE_PROFILE=1` выводит отдельные
стадии `llc`, translation audit, `cuModuleLoadData`, CUDA Graph
capture/instantiate. Число уникальных функций определяется точно
из compiled plan; сравнение с историческими 63 707 *entrypoints*
имеет смысл лишь после фактического измерения BPTT=16.

**Критерий завершения:** BPTT8 и BPTT16 завершают GPU prepare и
replay, записаны graph nodes, уникальные PTX functions, LLVM size,
JIT/graph/replay wall-time, device event time и бюджет тензоров.
Для реального измерения peak VRAM ещё потребуется отдельная аппаратная
телеметрия; эти логи его не доказывают. Пока нельзя утверждать, что
BPTT16 стабилен при обучении, быстрее в tokens/s или улучшает BPC.

## P0: доступный двухэтапный training/validation (код, GPU-приёмка ожидается)

Цель `NLL <= 1.5` считается **в натах на символ** для фиксированного
104-символьного алфавита. Эквивалентный предел BPC приблизительно 2.16404.
Это не прежний гипотетический `BPC <= 1.5`. Базовая метрика — длинная
validation; test не открывать до фиксации конфигурации и независимого
подтверждающего протокола.

- `task verify-torus16-p0`: CPU unit-тесты единиц измерения и лимитов,
  не аппаратная приёмка.
- `task train-torus16-p0`: rank4/BPTT4, 131072 train-символа,
  `AdamW LR=0.002`, `GPU_IR`, validation на 8192 символах
  каждые 32768 обучающих символов, test-suffix на 8192 символа
  зарезервирован и никогда не читается.
- `TORUS16_P0_PHASE=decay task train-torus16-p0`: отдельный
  `decay.ckpt` из **последнего** `base.ckpt`, не из best;
  продолжение до 262144 train-символов с LR=0.0004 при сохранённых
  AdamW moments и точном training cursor. `base.ckpt` не затирается.
  `decay.best.ckpt` вначале копирует validation-best из base.
- `TORUS16_P0_BPTT=8` выбирает отдельную директорию и граф
  с теми же бюджетами символов и периодичностью validation,
  но с меньшим числом AdamW updates. Это **не** контролируемый
  эксперимент, изолирующий эффект горизонта градиента.
- При P0 до LLVM/CUDA действуют три самостоятельных preflight:
  число graph kernels <= 40000, уникальных функций <= 4096,
  размеры материализованных графовых тензоров <= 256 MiB.
  Последний лимит **не измеряет полный peak VRAM**.
  Значения разрешено менять только явно и после изучения inventory.
- Отдельные лог-строки `validation_nll_nats`,
  `validation_final_nll_nats`, `validation_best_nll_nats`
  и `train_nll_nats_mean` сохраняют старый формат BPC.
  Вся процедура использует `TORUS16_SKIP_TEST=1`.

Подтверждением работоспособности будет локальный
`task verify-torus16-p0`, успешный BPTT4 preflight, завершённые
оба этапа на реальной RTX 5060 и воспроизводимые показатели NLL,
BPC, throughput, времени подготовки и потребления VRAM. Пока таких
новых GPU-измерений нет: P0 **реализован как протокол и код**,
но **эмпирически не закрыт**. Ни наличие CUDA Graph, ни доказательства
отдельных операций не гарантируют качества обучения или точности
аппаратного FP32.

Следующий этап после этого — контролируемая проверка Dynamic EMA,
а не возвращение к BPTT16.
 

## P1: селективная EMA и контролируемая ablation (исходники, GPU-приёмка ожидается)

Потребитель Torus16 теперь поддерживает два явно разделённых режима
`EmaMode::{Static, Selective}` (переменная `TORUS16_EMA_MODE`).
`Static` сохраняет исходную архитектуру и совместимость старых
checkpoint. `Selective` реализует в каждой ячейке:

```text
a_t = Conv9(LayerNorm(x_t))
alpha_t = sigmoid(decay_logit + a_t * decay_gate)
s_t = alpha_t * s_(t-1) + (1-alpha_t) * (k_t * v_t)
```

`decay_gate` имеет форму [1,48] на блок и инициализируется нулём,
то есть первый forward математически совпадает со статической EMA;
новая архитектура получает отдельный Semantic IR/identity,
а checkpoint не допускает неявного перекрёстного resume. Старый
TorusShared warm-start переносит исторические параметры, а новые gates
остаются нулевыми. Ни особых CUDA kernels, ни дополнительного lowering
в ядро VeriNeural не добавлено; это композиция `Mul/Add/Exp/Div`.

`task verify-torus16-p1` проверяет Rust inventory, размерности,
привязку и независимый скалярный oracle. GPU oracle:
`task verify-gpu-torus16-p1` (выполняет разработчик на NVIDIA).
`task train-torus16-p1` обучает static/selective на одинаковом
BPTT4 (BPTT8 opt-in), rank4 (rank8 opt-in), seed, warm-start,
бюджете train-символов и 8192-char validation; test не читается.
Проверяются best/final validation NLL (наты), BPC, throughput,
число kernels и реальная цена подготовки.

`p1_gate_diagnostics` сообщает bias-only sigmoid и нормы
параметров `mix_gate/decay_gate`; **это не измерение реальных
gate активаций и не критерий успешного динамического забывания**.
Нужны дальнейшие input-conditioned trace/ablation на holdout.
Rank8 нельзя объявить лучше rank4 без отдельных сопоставимых
прогонов. Улучшение validation не считается достигнутым до
локального GPU запуска с несколькими seeds. BPTT16/32 исключены.

### P1 mix-bias ablation

`TORUS16_P1_MIX_BIAS_INIT=zero task train-torus16-p1` повторяет
парный static/selective эксперимент, но принудительно обнуляет
`mix_bias_{layer}_{role}` **после** weight-only warm-start.
`preserve` (по умолчанию) сохраняет обученные значения из исходного
checkpoint. Это изменяет initial bindings и architecture fingerprint,
поэтому сравнение запускается в отдельном каталоге `mix-zero/`
(основной baseline — `mix-preserve/`). `TORUS16_SKIP_TEST=1`
обязателен в обоих режимах. Тесты проверяют согласованное
обновление значений в параметрах и bindings. Абляция должна
сравниваться на одинаковом бюджете train-символов; вывод
`mix_bias_only_sigmoid_mean` нельзя выдавать за измеренный gate
на конкретных токенах. Никакого результата по NLL до GPU-прогонов нет.

## P2: управляемое увеличение глубины (код в dev, NVIDIA-приёмка ожидается)

Разработка P2 сохраняет исходные четыре блока и ширину 48. API
`Ema4Weights::with_depth(4|6|8)` добавляет 2 или 4 блока без
изменения базовых имён. Отдельный
`architecture_model_for_configuration(vocab, matrix, ema, depth, residual)`
собирается только публичными примитивами VeriNeural. Он не изменяет
`architecture_model_for_ema` и исторические checkpoint.

При `residual=true` память и FF-ветвь каждого блока имеют по одному
обучаемому скаляру после прежнего коэффициента 0.5:
`x <- x + 0.5 * residual_mem_scale * delta` и
`x <- x + 0.5 * residual_ff_scale * down`. Для первых четырёх блоков
скаляры инициализированы единицами, для новых блоков нулями.
Это позволяет стартовать с функцией, близкой к исходной модели,
и затем обучать новые residual-вклады без немедленного большого
возмущения. Conv9/EMA состояния новых слоёв всё равно обновляются.

Исторический TorusShared checkpoint проверяется по прежнему
четырёхблочному инвентарю. Переносятся только совместимые веса,
но не optimizer moments/cursor/state. Новые слои получают
детерминированные веса. Глубина, остаточные скаляры и их значения
учитываются при проверке training graph/checkpoint; без явного
resume cross-depth перенос запрещён.

Команды:

```sh
task verify-torus16-p2
task verify-gpu-torus16-p2
task train-torus16-p2
TORUS16_P2_DEPTH=8 task train-torus16-p2
```

`train-torus16-p2` сравнивает 4 и 6 (либо 4 и 8) блоков
с `RoleDelta4`, `BPTT4` по умолчанию, одинаковым
seed, историческим warm-start, 16384 новыми обучающими символами,
8192-символьной validation и закрытым test.
EMA по умолчанию static, `TORUS16_P2_EMA=selective` допускает
отдельный эксперимент. Ограничены 40000 графовых kernels,
4096 уникальных PTX-функций и 256 MiB материализованных
графовых тензоров до LLVM/CUDA JIT. Это **не** предел peak VRAM;
нужна отдельная NVIDIA-телеметрия и фактический замер
времени до качества.

**Ширина 64 ещё не реализована.** Низкоуровневые вращения,
проекционные матрицы и shape contracts Torus16 зафиксированы
на WIDTH=48. `TORUS16_P2_WIDTH=64` явно отвергается, чтобы
случайно не объявить иной алгоритм тем же Torus16.
Разработка ширины 64 допускается лишь после GPU acceptance
глубины 6/8 и подтверждения, что дополнительная ёмкость
оправдывает время обучения на RTX 5060 (8 GB VRAM).

Статус: наличие исходников и unit/NVIDIA-test сценариев
**не означает** их прохождения, уменьшения NLL или
сертификации LLVM/PTX/SASS/аппаратного FP32.
